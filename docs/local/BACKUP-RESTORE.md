# Local backups, recovery and updates

A complete local backup needs the database, backend/.env (encryption key), backend/storage/app/private, local-runtime/settings.json, source version/dependency manifest and relevant logs/audit evidence. Keep backups private, encrypted where available, outside the served application folder, and verify restoration. A database-only backup loses uploaded originals and PDFs. Do not email backups or include them in a distributable ZIP.

For the default SQLite setup: wait for jobs to finish, run local/Stop.ps1 and confirm its process record is gone. Copy the entire installed folder to a private backup location with normal Windows file tools while no process uses the database. Include local.sqlite and any WAL/SHM sidecars present. Verify checksums/file counts and preserve the app key. Restart the source only after the copy completes. Never copy a busy SQLite file alone. For MariaDB use a consistent service-aware database backup as well as private files; the provided scripts do not implement server backup/conversion.

Restore into another NEW folder rather than overwriting a running installation. Retain the old copy. Review every absolute path in local-runtime/settings.json and backend/.env: Root, Php/Python/Node/Browser, DB_DATABASE, DOCUMENT_PYTHON and PDF paths must identify the restored installation/prerequisites. Keep the original APP_KEY. Clear only compiled caches through artisan optimize:clear in the restored backend, then Health/Start and verify login, known records, source downloads and PDF generation. The restoring operator must explicitly update paths; Start deliberately refuses silent relocation. Never run two copies using the same database/private storage.

Updates: stop and back up first. Extract the new package into a fresh versioned folder. Copy the stopped installation's private database/storage/environment/settings, preserving APP_KEY and accounts, into the new folder; update the absolute paths just described. Use the new package's vendor/renderer dependencies and React build. Review additive migration notes, run `php artisan migrate --pretend` and then `php artisan migrate --force` against the private restored copy only. No migrate:fresh, reset or seeding defaults. Clear compiled caches, run Health and the Team Lead checklist, then switch your shortcut to the new folder. Keep the previous folder and compatible backup for rollback. Do not overwrite dependencies over the running old installation.

Code rollback and database restore are different actions. Never automatically migrate:rollback retained audit/history. If a schema change prevents old code from running, use the reviewed compatible backup after stopping all services. Backups may contain data intentionally deleted from the live application: apply the company's separate backup retention/access policy.
